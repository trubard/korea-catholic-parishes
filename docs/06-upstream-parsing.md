## 0. 요약

문제는 둘이지만 뿌리가 같다. **`raw` 에 있는 정보가 파싱에서 사라진다.**

| | |
|---|---|
| **A. 시각이 덜 뽑힌다** | 토·주일 구간 282건 중 **131건(46.5%)**. 그중 11건은 결과가 통째로 빔 |
| **B. 종류가 분류되지 않는다** | `type` 이 있는 2,313건이 **전부** `note` 도 갖고 있다 — `type` 은 `note` 에서 낱말을 골라낸 파생값이라 어휘에 없으면 조용히 샌다 (83건 + 축일 465건) |

A 는 §1~§9, B 는 §10~§14 에서 다룬다. 둘 다 **정보가 `note` 문자열에 갇혀
있다**는 같은 증상이고, 소비하는 쪽에서 문자열 매칭으로 되짚고 있다.
그 되짚기에는 **추측이 섞인다.**

빠진 시각은 대개 `note` 에 문자열로 남는다.

```json
{ "time": "10:30", "note": "17/19" }     ← 17시·19시 미사가 사라진다
```

소비 쪽에서 이 `note` 를 되살려 **124건의 미사를 복구**했다.
대전교구 공식 페이지와 대조해 복구 결과가 맞는지 확인했다 — 둔산동 주일
`6/8:30/10:30/17/19`, 목동 토요일 `9/16(어린이)/18(중고등부,특전)`, 궁동
토요일 `10/15/19` 모두 공식 페이지와 일치한다.

**더 확실한 근거는 `raw` 그 자체다.** 복구 결과를 `raw` 와 나란히 놓고 보면
글자까지 맞는다. 즉 정보는 이미 `raw` 에 다 있고, 파싱에서만 빠진다.

## A부 — 시각이 덜 뽑히는 문제

## 1. 구분자를 넓게 잡는다

가장 큰 원인이다. 현재는 슬래시로 이어진 시각을 **첫 번째만** 뽑는 듯하다.

```
raw     ▶주일 - 6/8:30/10:30/17/19
결과    time=6:00, time=8:30, time=10:30(note="17/19")
기대    6:00 · 8:30 · 10:30 · 17:00 · 19:00
```

구분자로 실제 등장하는 것들:

| 구분자 | 예 |
|---|---|
| `/` | `8/10:30/18` |
| `,` | `15시(어린이), 17시` |
| 공백 | `새벽 06:30 교중10:00` |
| 없음(붙여쓰기) | `10시30분(교중)` |

**제안** — 구간 문자열에서 시각 토큰을 **전부** 훑고, 나머지를 설명으로 붙인다.
"앞에서부터 하나씩 끊는" 방식이면 어디선가 반드시 멈춘다.

---

## 2. 괄호 안의 쉼표에서 끊기지 않게

`(첫토, 성모신심미사)` 처럼 **괄호 안에 쉼표**가 있으면 거기서 잘린다.
157건이 이 형태를 갖고 있고, 그중 8건이 실제로 깨졌다.

```
raw     ▶토요일 - 10(첫토, 성모신심미사)/17
결과    [{ "time": "10:00", "note": "(첫토" }]        ← 17시가 사라지고 note 도 잘림
기대    10:00 (첫토, 성모신심미사) · 17:00
```

같은 원인의 다른 사례:

```
raw     ▶토요일 - 9/16(어린이)/18(중고등부,특전)
결과    [{ "time":"09:00", "note":"16(어린이)/18(중고등부", "type":["어린이","중고등부"] }]
기대    09:00 · 16:00(어린이) · 18:00(중고등부, 특전)
```

여기서 두 가지가 함께 어긋난다.

1. 16시·18시 미사가 사라진다
2. **종류가 한 항목에 뭉친다** — 9시가 "어린이 중고등부" 가 된다

두 번째가 B 문제와 만나는 지점이다(§10). 어느 종류가 어느 시각의 것인지
소비 쪽이 문자열로 되짚어야 한다.

**제안** — 괄호/대괄호는 **짝을 맞춰** 통째로 하나의 토큰으로 다룬 뒤,
그 바깥의 구분자로만 끊는다. 괄호 안의 설명은 **바로 앞 시각의 것**이다.

## 3. 한글 시각 표기를 인식한다

`10시` · `10시 30분` · `오후 5시` 형태가 231건 있다.

```
raw     ▶토요일 - 15시/18시30분
결과    [{ "time": "15:00", "note": "시/18시30분" }]
기대    15:00 · 18:30

raw     ▶토요일 - 오후5시 토요가정미사
결과    []                                   ← 통째로 사라진다
기대    17:00 (토요가정미사)
```

**제안** — 시각 토큰 정규식에 다음을 포함한다.

```
(오전|오후)?\s*(\d{1,2})\s*시(\s*(\d{1,2})\s*분)?
(\d{1,2}):(\d{2})
(\d{1,2})                       ← 구분자에 둘러싸인 홑숫자
```

`오후 5시` 는 17:00 으로, `오전 6시` 는 06:00 으로 정규화한다.
다만 **`11월` 처럼 뒤에 `월` 이 오면 시각이 아니다** — 계절 안내에서 자주 나온다.

## 4. 구분 기호가 하이픈이 아닌 경우

`▶토요일 - ` 를 전제하면 다음이 빠진다. 드물지만(3건) 결과가 통째로 비므로
피해가 크다.

```
raw     ▶토요일_18:00                  ← 언더스코어
raw     ▶토요일 19:30(동.19)            ← 기호 없음
raw     ▶토요일: 15시(어린이), 17시      ← 콜론
```

**제안** — `▶\s*(구간명)\s*[-_:–—]?\s*` 로 느슨하게 받는다.

## 5. 별도 구간명을 놓치지 않는다

`▶토요일` · `▶주일` 외에 다른 이름이 쓰인다.

```
raw   ▶토요일 - 10[매월 첫주간 토요일],
      ▶토요특전 - 14(상홍리공소 매월 첫주간 토요일 제외)/16/18,
      ▶주일 - 6/8:30/10:30/19/
```

`▶토요특전` 을 모르면 토요일 저녁 미사 세 대가 통째로 빠진다.
실제로 발견된 것: `토요특전`(1건) · `공소` · `상월공소 주일미사`.
지금은 드물지만, 구간명을 열거 방식으로 두면 새 표기가 생길 때마다 조용히
누락된다. §14 의 "열거하지 말자" 와 같은 이야기다.

**제안** — 알려진 구간명을 열거하되, **모르는 `▶` 구간도 버리지 않고**
`extra` 같은 자리에 원문을 남긴다. 소비 쪽이 판단할 수 있다.

## 6. 계절·조건 표기는 시각과 분리한다

61건이 동절기/하절기 안내를 담고 있다.

```
raw     ▶토요일 - 19(하.19:30) *하절기:4월~9월
결과    [{"time":"19:00","note":"(하."}, {"time":"19:30","note":") *하절기:4월~9월"}]
```

두 항목으로 쪼개졌는데 **둘 다 note 가 깨졌다.** `19시` 와 `하절기 19시 30분` 은
같은 미사의 두 얼굴이지 별개의 미사가 아니다.

```
raw     ▶주일 - 6(동.7)/10(교중) *동절기(11-3월)
기대    06:00 (동절기 07:00) · 10:00 (교중)
```

**제안** — 구간 끝의 `*` 이후는 **구간 전체의 단서**로 보고 각 시각의 `note`
에 섞지 않는다. `(동.7)` 처럼 시각에 붙은 계절 대안은 별도 필드
(`seasonal: { winter: "07:00" }`)로 둔다 — §12 의 ⑤ 와 같은 필드다.
지금은 판단할 근거가 없어 **소비 쪽에서는 계절 조건을 아예 적용하지 않는다**
(있는 미사를 없다고 말하는 것이 더 나쁘기 때문).

## 7. UI 문구·게시글이 섞여 들어온다

수집 대상 페이지의 다른 요소가 `note` 에 붙는다.

| 유형 | 건수 | 예 |
|---|---|---|
| UI 문구 | 17 | `(미사예물입력불가성모승천대축일)` |
| 본당 게시글 전문 | 18 | 365자짜리 주보 공지 · 이용약관 · 운영자게시판 |
| 문장이 잘린 조각 | 352 | `(첫토` · `성모신심)` · `(하.` |

정상 비고는 **99%가 22자 이하**다. 30자를 넘는 18건은 전부 사고였다.

**제안**
- 스크래핑 시 미사시간 영역만 선택자로 좁힌다 (`미사예물입력불가` 는
  그 페이지의 버튼 라벨로 보인다)
- 결과 검증에 **길이 상한**과 **괄호 짝 검사**를 넣는다. 둘 중 하나라도
  걸리면 파싱 실패로 보고 `note` 를 버리거나 원문을 `raw_note` 로 옮긴다

## 8. 오탈자

원본 그대로 두는 것이 원칙이지만, 뜻이 명백히 어긋난 것은 짚어 둔다.

| 표기 | 건수 | 올바른 표기 |
|---|---|---|
| 성모 **성천** 대축일 | 4 | 성모 승천 |
| **승모** 승천 대축일 | 1 | 성모 승천 |

성당이 손으로 적은 안내라 생기는 것이고, 상류가 고칠 문제는 아닐 수 있다.
소비 쪽에서 교정하고 있다. 다만 **표기 흔들림**(`성모 승천` / `성모승천`)은
틀린 게 아니므로 건드리지 않는다.

## 9. 검증 방법 제안

파서를 고친 뒤 회귀를 막는 방법이다. 소비 쪽에서 실제로 쓴 것이다.

### 9-1. raw 대비 시각 개수

```
raw 구간에서 뽑은 시각 개수  >  파싱 결과 개수   →  누락 의심
```

이 하나로 131건을 잡았다. `11월` 같은 오탐은 뒤에 `월` 이 오는지로 걸러낸다.

### 9-2. 교구 공식 페이지와 대조

대전교구는 `djcatholic.or.kr/home/pages/church.php?area={지구}` 한 페이지에
전 성당의 미사시간이 들어 있다(EUC-KR). 성당 블록을 잘라 시각을 뽑으면
자동 대조가 된다.

주의: 블록 경계를 넉넉히 잡으면 **다음 성당 정보를 삼킨다.** `미사시간`
부터 `×` 또는 `본당 상세정보` 전까지로 끊어야 한다 (이걸로 처음에 오탐 5건이
났다).

### 9-3. 결과가 통째로 빈 구간

`raw` 에 시각이 있는데 배열이 `[]` 면 100% 사고다. 11건 있었다.

### 9-4. 분류 누락 (§10 이후를 적용한 뒤)

`note` 에 `청년` 이 남아 있는데 `audience` 가 비어 있으면 파서가 못 뽑은 것이다.
필드를 나누면 이 검사가 성립한다 — 지금 구조로는 성립하지 않는다(§13).

## B부 — 종류가 분류되지 않는 문제

## 10. `type` 은 `note` 의 파생값이다

| | 건수 |
|---|---|
| 미사 항목 전체 | 17,348 |
| `note` 있음 | 5,859 |
| `type` 있음 | 2,313 |
| **`type` 이 있는데 `note` 가 없는 것** | **0** |

마지막 줄이 핵심이다. **`type` 은 `note` 에서 낱말을 골라낸 파생값**이고,
독립된 정보가 아니다. 그래서 두 가지가 동시에 일어난다.

- **같은 뜻이 두 곳에 흩어진다** — `(청년미사)` 는 note 이면서 `type:['청년']`
- **어휘에 없으면 통째로 샌다** — `주일학교` 는 어느 `type` 에도 못 들어간다

### note 안에 실제로 섞여 있는 것들

한 문자열에 성격이 다른 정보가 겹쳐 들어온다. 축별로 세면(중복 포함):

| 축 | 건수 | 예 |
|---|---|---|
| **대상** — 누가 참례하는가 | 1,084 | `어린이` `청년` `중고등부` `주일학교` |
| **전례 성격** — 어떤 미사인가 | 938 | `교중` `특전` `성모신심` `위령` |
| **축일** — 그날이 무슨 날인가 | 600 | `성모승천대축일` `주님 성탄 대축일` |
| **되풀이 조건** — 언제만 하는가 | 193 | `매월 첫 토요일` `첫주 제외` |
| **계절** — 시각이 바뀌는가 | 146 | `동절기 19시` `하.19:30` |
| **장소** — 어디서 하는가 | 118 | `노송공소` `상홍리공소` |
| 위 어디에도 없음 | 3,005 | `평일미사` `10시 미사` `저녁미사` |

마지막 3,005건이 절반이다. 대부분 **시각·요일을 한 번 더 말한 것**이라
정보가 없다 — `10:00` 항목의 note 가 `10시 미사` 인 식이다.

### 한 줄에 여러 축이 섞인 사례

```
(성모 승천 대축일 11시 교중미사)     축일 + 시각 + 전례성격
(성모승천대축일 09시 주일학교)        축일 + 시각 + 대상
(성모 승천대축일 10시(초중고 주일학교)) 축일 + 시각 + 대상 둘
```

소비하는 쪽에서 이걸 되짚으려면 문자열 매칭에 기대야 한다.
실제로 `11(신심)/16(학생)` 이 `type:['학생','신심']` 으로 뭉쳐 온 것을
라벨 문자열로 되짚어 나눴다 — §2 에서 본 그 사례다. **추측이 섞인다.**

## 11. 구체적인 문제 세 가지

### 11-1. `type` 어휘에 없으면 정보가 샌다

note 에 대상이 적혀 있는데 `type` 이 빈 항목이 **83건**이다.

| 놓치는 낱말 | 건수 |
|---|---|
| 주일학교 | 49 |
| 초등부 | 40 |
| 중고등 (`중고등부` 아님) | 5 |
| 베트남 · 필리핀 · 중국어 | 6 |
| 장애 · 수화 | 3 |
| 유치부 · 첫영성체 · 위령 · 연도 | 4 |

`중고등부` 는 어휘에 있는데 `중고등` 은 없다. 이런 식의 사각지대는
어휘를 늘려도 계속 생긴다 — **열거 방식의 한계**다(§14).

### 11-2. 축일이 `type` 에 안 들어온다

대축일은 `note` 에 글자로만 온다. 토요일 대축일 미사 561건 중
**465건(83%)이 `type` 이 비어 있다.**

이 때문에 소비 쪽 목록 카드에 아무 표시도 안 나왔고,
날짜 계산으로 따로 판단해 메꿔야 했다.

### 11-3. 정보가 이중화돼 어느 쪽을 믿을지 모른다

`(청년미사)` 는 note 이면서 `type:['청년']` 이다. 화면에 둘 다 쓰면
`청년 청년미사` 가 된다. 소비 쪽에서 "배지가 이미 말한 것은 note 에서 뺀다"는
규칙을 따로 만들어야 했다.

같은 note 에 `type` 이 갈리는 경우도 있다 — `특전` 이 어떤 항목에는
`type:['특전']` 이고 어떤 항목에는 없다.

---

## 12. 제안 — 축별로 필드를 나눈다

`note` 하나에 다 담지 말고, **성격이 다른 것은 다른 자리에** 둔다.

```jsonc
{
  "time": "18:00",

  // ① 대상 — 누가 참례하는가 (열거 아닌 자유 문자열)
  "audience": ["청년"],

  // ② 전례 성격 — 어떤 미사인가
  "kind": ["교중"],          // 교중 · 특전 · 신심 · 위령 · 성시간 …

  // ③ 축일 — 그날이 무슨 날인가
  "feast": "성모 승천 대축일",

  // ④ 되풀이 조건 (이미 recurrence 로 있다)
  "recurrence": { "weeks": [1], "raw": "매월 첫 토요일" },

  // ⑤ 계절 대안 — 같은 미사의 다른 시각 (§6)
  "seasonal": { "winter": "19:00" },

  // ⑥ 장소 — 본당이 아닌 곳
  "place": "노송공소",

  // ⑦ 위 어디에도 안 들어간 나머지 (원문 보존)
  "note": "가족 초대 미사"
}
```

### 왜 이렇게 나누는가

| 축 | 소비하는 쪽이 이걸로 하는 일 |
|---|---|
| 대상 | 배지 표시 · "어린이 미사 빼고 보기" 같은 필터 |
| 전례 성격 | 교중미사 강조 · 주일 의무 판정(`특전`) |
| 축일 | 그날 안내 · 의무 축일 판정 |
| 되풀이 | **그날 실제로 있는지** 판정 — 없는 미사를 보여주면 헛걸음 |
| 계절 | 지금 시기에 맞는 시각 표시 |
| 장소 | 본당이 아닌 곳임을 알림 — 찾아갔는데 없으면 낭패 |

지금은 이 판단들이 전부 문자열 매칭 위에 서 있다.

### 핵심 원칙

**`note` 는 "분류하지 못한 나머지" 여야 한다.**

지금은 반대다 — note 가 원본이고 `type` 이 거기서 뽑은 조각이라,
뽑기에 실패하면 조용히 샌다. 뒤집으면 실패가 드러난다.
`note` 에 여전히 `청년` 이 남아 있다면 그건 파서가 못 뽑은 것이고,
검증에서 잡을 수 있다(§9-4).

---

## 13. 단계적 이행

한 번에 바꾸면 소비하는 쪽이 다 깨진다. 순서를 제안한다.

### 1단계 — `type` 은 그대로 두고 축일만 뺀다

가장 크게 새는 곳이고(465건) 성격도 명확하다.

```jsonc
{ "time": "18:00", "feast": "성모 승천 대축일", "type": ["청년"], "note": "(성모승천대축일 청년미사)" }
```

`note` 를 그대로 두면 기존 소비자가 깨지지 않는다.

### 2단계 — `type` 을 `audience` 와 `kind` 로 가른다

지금 `type` 에는 성격이 다른 둘이 섞여 있다.

| 대상(`audience`) | 전례 성격(`kind`) |
|---|---|
| 어린이 · 유아 · 학생 · 청소년 · 중고등부 · 초등부 · 주일학교 · 대학생 · 청년 · 장년 · 가족 | 교중 · 특전 · 신심 · 성시간 · 위령 · 연도 |

섞여 있어서 소비 쪽에서 우선순위 함수를 따로 만들어
"어린이 미사를 성인에게 대표로 보여주지 않기" 를 처리하고 있다.
나뉘어 오면 그 판단이 훨씬 단순해진다.

`type` 은 당분간 둘을 합친 값으로 유지하면 하위 호환이 된다.

### 3단계 — 계절·장소를 뺀다

건수는 적지만(146 · 118) **지금은 아예 못 쓰는 정보**다.
계절 조건은 판단 근거가 없어 소비 쪽에서 적용을 포기했고(§6),
공소는 본당과 구분되지 않아 그냥 미사로 보인다.

---

## 14. 어휘를 열거하지 말자는 제안

`type` 이 새는 근본 원인은 **아는 낱말만 뽑기** 때문이다.
`중고등부` 는 알고 `중고등` 은 모른다. §5 의 구간명 문제와 같은 구조다.

대안: 괄호 안 내용을 **일단 통째로 담고**, 알려진 어휘면 분류하되
모르면 원문 그대로 남긴다.

```jsonc
// 아는 낱말
{ "audience": ["중고등부"] }

// 모르는 낱말 — 버리지 않는다
{ "audience": ["베트남어"], "audience_raw": "베트남어 공동체" }
```

소비하는 쪽은 모르는 값을 만나면 **그대로 표시**하면 된다.
지금처럼 조용히 사라지는 것보다 낫다.

## C부 — 남은 것

## 15. 소비 쪽에서 이미 하고 있는 일

상류가 안 나눠 줘서 소비 쪽에서 만든 것들이다. 상류에서 하면 없어진다.

| 소비 쪽 함수 | 하는 일 | 상류가 고치면 |
|---|---|---|
| `recoverTimes` | note 에 갇힌 시각 되살리기 | 파싱이 고쳐지면 불필요 (A) |
| `isFeastDayMass` | note 에서 `대축일` 찾기 | `feast` 를 보면 됨 |
| `massTypeRank` | 대상/성격 섞인 type 에 우선순위 | `audience`·`kind` 로 분리되면 단순해짐 |
| `noteBeyondBadges` | 배지와 겹치는 note 감추기 | note 가 "나머지" 면 겹칠 일이 없음 |
| `shortFeastNote` | note 에서 축일 이름만 자르기 | `feast` 를 그대로 씀 |
| `meaningfulNote` | 잘린 조각·게시글 걸러내기 | 여전히 필요 (§7) |
| `correctSchedule` | 오탈자 교정 | 상류가 고칠 문제가 아닐 수 있음 (§8) |

일곱 중 넷이 **분류 문제**에서, 하나가 **파싱 문제**에서 나왔다.

## 16. 잔여 케이스 — 판단이 필요한 것

소비 쪽 복구로도 해결되지 않은 것들. 상류가 원문 구조를 알고 있으니
더 정확히 판단할 수 있다.

| 성당 | raw | 문제 |
|---|---|---|
| 내동 | `매월 첫 토요일 10시 / 매주 어린이, 청년 미사 18,` | 결과 `[]` — 문장형이라 못 읽음 |
| 성환 | `오전6시(하절기 3월-10월) / 오전 7시 (동절기 11월-2월) 10시30분(교중) 소동공소(첫째주 15시)` | 결과 `[]` — 계절·공소가 한 줄에 |
| 강경 | `19:30(동.19), * 동절기 11월~2월` | 결과 `[]` |
| 세종성베드로 | `어린이미사16(첫주제외)/ 19(특전미사) *첫토요일/10:00(성모신심미사)` | 10시 누락 |
| 삼성동 | `18 *매월 첫주 10/18` | 조건부 10시 — 매주가 아니므로 판단 필요 |
| 천안봉명동 | `19(첫 토요일 - 10시, 성모신심미사)` | 조건부 10시 |
| 천안쌍용3동 | `8/10:30 매월 마지막주 토 15시 어린이미사는 **가정주일로 없음**` | 15시는 **없다는 안내** — 넣으면 안 된다 |

마지막 항목이 중요하다. **"없음" 안내를 미사로 읽으면 사용자가 헛걸음한다.**
부정 표현(`없음` · `제외` · `쉽니다`)이 붙은 시각은 넣지 않는 편이 안전하다.

## 17. 정리

두 문제의 뿌리는 같다. **`note` 가 원본이고 나머지가 거기서 뽑은 조각**이라,
뽑기에 실패하면 조용히 샌다.

- 시각이 새면 → **미사가 화면에서 사라진다** (131건 / 46.5%)
- 종류가 새면 → **배지·필터·의무 판정이 안 된다** (83건 + 축일 465건)

고치는 방향도 하나다. **`raw` 에서 축별로 뽑아내고 `note` 를 "나머지" 로 둔다.**
그러면 실패가 드러나고 검증이 성립한다(§9).

이행 순서 제안: **파싱(§1~§4) → 축일(§13-1) → 대상/성격(§13-2) → 계절·장소(§13-3)**.
파싱을 먼저 두는 이유는 지금 미사가 실제로 화면에서 빠지고 있기 때문이고,
나머지는 `note` 를 유지하는 한 기존 소비자를 깨뜨리지 않는다.
